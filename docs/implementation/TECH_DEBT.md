## Accepted in this rebuild

| Item | Description | Disposition |
|---|---|---|
| `fan_memories` has no version history table yet (spec 8.37: created/updated/confirmed/contradicted/expired should be historized) | Phase 6 vertical slice stores only current state; contradictions are overwritten (most recent wins), not journaled | Add `fan_memory_versions` when a feature actually needs the history (e.g. an audit view or a "why did this change" trace) |
| `fan_scores` has no history table (spec 9.9 implies score evolution should be traceable over time, not just the current value) | Same reasoning — one current row per fan, `version` int increments but old values aren't kept | Add score history once Analytics (Phase 12) or Benchmark needs a time series |
| AI analysis now runs automatically after every message (no Budget Guards yet — spec 5.29) | Owner explicitly required automatic analysis over a manual button; no per-agency/per-conversation rate limiting or cost cap exists yet, so a very chatty mock conversation calls the AI on every single message | Add budget guards (max analyses/conversation/hour, or debounce rapid-fire messages) before this runs against real, high-volume conversations — currently fine at mock-testing volume |
| No live push for Fan Intelligence updates — the panel picks up the automatic AI analysis via a second `router.refresh()` fired ~4s after sending a message (a fixed guess, not a real completion signal) | Simplest thing that works without adding Supabase Realtime/websocket infrastructure for a 2-task MVP | If the fixed delay proves unreliable (slow AI calls, fast networks) or feels laggy, replace with a Supabase Realtime subscription on `fan_scores`/`fan_memories` so the panel updates the instant the row changes |
| AI Gateway has two model tiers (Fast/Haiku, Standard/Sonnet) but no escalation logic or fallback chain (spec 5.7, 5.11, 5.19) — a task always uses its one assigned model, never retries on a different one | Only 3 tasks exist so far; building tiering/escalation logic now would be scaffolding without enough data points to justify it | Revisit once more tasks exist and there's real signal on where a fixed model choice underperforms |
| No Benchmark / eval harness (spec Part 30) exists yet — prompt quality was only caught by the owner manually reading one test conversation, which is exactly how `memory-extraction-v1` shipped with the category-misuse bug (see BUILD_PROGRESS.md) | Part 30's full Benchmark/Gold Dataset machinery is explicitly a later phase, not Phase 7 | Before Phase 11 (Full AI) goes anywhere near real fans, a minimal eval set (a handful of hand-labeled mock conversations checked on every prompt change) should exist — flagged here so it isn't forgotten |
| Copilot has no Response Validator (spec 11.27 — price/media/script/permission/platform-rule checks before a suggestion is shown) | There is nothing to validate against yet: no Script Engine (Phase 9), no Pricing Engine/media catalog (Phase 10). The prompt itself instructs the AI to never invent prices/offers, which is a prompt-level guard, not a deterministic validator | Build the real Response Validator once Script/Pricing/Media engines exist and there are actual rules to check a suggestion against |
| No Duplicate Prevention or Repetition Detection (spec 11.37, 11.38) — nothing stops the AI from suggesting the same phrasing twice in a row, or a chatter double-sending | Out of scope for a single-suggestion-at-a-time MVP with a human always clicking Send | Add once Copilot sees real multi-conversation daily use and repetition actually shows up as a problem |
| Human Edit Tracking data (`copilot_suggestions.edit_distance`, spec 11.30) is recorded but nothing reads it yet — no quality dashboard, no feedback loop | Spec 11.30 itself says this data must not auto-train the model; it's meant to feed future analysis/Benchmark, not to be acted on immediately | Wire into Conversation Quality Metrics (spec 11.39) when Analytics (Phase 12) is built |
| Structured output isn't schema-validated (spec 5.13/11.28) — `parseJsonResponse()` only checks the text is valid JSON, not that it matches the expected shape (e.g. a missing field, wrong type). No retry-with-correction or fallback chain on validation failure | The two bugs already found (missing business context, unsupported `temperature` param) were both caught by a human reading the output, not by validation — this gap is real, not theoretical | Add a lightweight per-task schema check (even a hand-written type guard) before Phase 11 (Full AI) removes the human from the loop — a malformed decision must never reach a fan unreviewed |
| `ai_decisions.estimated_cost` is recorded per call but nothing surfaces it — spec 33's Milestone 3 gate explicitly requires "AI cost visible internally" | No internal dashboard exists yet (that's Phase 12 - Analytics) | Add a minimal cost view (even a raw `sum(estimated_cost) by decision_type` query on an admin page) before real pilot traffic, so a runaway cost isn't discovered by surprise |
| Script Engine (Phase 9) only has 2 node types (message, paid_media) — no CONDITION, WAIT, NEGOTIATION, HUMAN_APPROVAL, CUSTOM_REQUEST, RECOVERY node types from spec 13.7/28.39, and no Media Selector (spec 13.10) or dynamic pricing rules (spec 13.11) | The underlying schema (generic node/edge graph) supports adding these as new rows, not a rewrite — but the runtime engine (`advanceScriptRun`) only knows how to execute the 2 types it has | Add node types as the features they depend on land: WAIT needs a scheduler (not built), NEGOTIATION needs the Negotiation Engine (Phase 6 in spec 33's own numbering, later than Script Engine), HUMAN_APPROVAL needs a review queue |
| Script Builder has no graph validation beyond "has a real step" and "paid steps have a price" (spec 13.38's fuller list: broken references, impossible branches, no end path, infinite loops, permissions) | The linear-sequence builder (forms/cards, not a visual graph editor) makes most of those structurally impossible to create in the first place — e.g. you cannot reference a node that doesn't exist because branch targets are a dropdown of real nodes | Revisit once/if a freer graph editor (spec 13.34's future visual canvas) lets an agency build genuinely invalid graphs |
| No Script Analytics UI (spec 13.40-13.43: entries/conversion/revenue/branch distribution/Script Health Score) — the raw events are captured in `script_run_events`, nothing reads them | Analytics is explicitly Phase 12 | Build the dashboards once Analytics exists; the event data is already there and shouldn't need backfilling |
| Adaptive script messages (`generation_mode: 'adaptive'`, `SCRIPT_MESSAGE` task) reuse the same un-validated JSON parsing and no-retry behavior as the rest of the AI Gateway (see the structured-output row above) | Same root cause, not new to this feature | Covered by the same fix (schema validation before Phase 11) |
| Script step delays (`script_nodes.delay_seconds`, spec 11.10/28.38) have no real background scheduler — `checkDueScriptRuns()` only fires when `/inbox/[id]` happens to be loaded by a human. A due step with nobody looking at the conversation just sits there | Vercel Cron is the obvious real mechanism, but (a) Cron only runs against Production deployments, not Preview — useless for the environment we've actually been testing in — and (b) Hobby-tier Vercel plans cap Cron at once/day, too coarse for minute-scale delays anyway | Before trusting delays in real usage: confirm the Vercel plan supports frequent Cron, add a `/api/cron/...` route using `createAdminClient()` (already exists, used elsewhere) once on Production, and keep `checkDueScriptRuns()` as a redundant catch-up rather than removing it |
| Delay duration is a flat number the agency types in — no coherence check against what's actually being sent (e.g. a 2-minute video shouldn't be followed by a message 5 seconds later) | `media_assets.duration_seconds` now exists (Phase 10) but nothing populates or reads it yet — no metadata extraction on upload, no engine logic ties delay to it | Wire duration extraction (spec 14.13, "no LLM needed") on upload, then have the script builder suggest/require a delay proportional to it for that step |
| Upload only trusts the browser-provided MIME type (`file.type`) to classify image/video/audio — spec 14.48 explicitly warns "never trust the client-provided name or MIME type alone" | No server-side content sniffing (magic-byte check) or file-size cap exists yet. The upload path also moved fully client-side (browser → Supabase Storage directly, to work around Server Actions' 1MB body limit and Vercel's ~4.5MB function payload cap), so there's now no server hop to add a check to without introducing one on purpose | Add before opening uploads beyond the owner's own testing — either a size/type check in a Storage trigger/Edge Function, or a post-upload verification step before a media is marked `active` |
| No AI Media Selection/Ranking, semantic search, bundles, duplicate-sale awareness, or performance-based recommendations (spec 14.20-14.32, 14.46-14.47) — an agency (or script) always picks the exact media asset by hand | All of Media Intelligence's "choose the right content automatically" layer is explicitly later scope; this phase only had to prove a real, price-safe asset can be sold | Build once Full AI (Phase 11) or Copilot needs to suggest media autonomously rather than following a human-authored script |
| No Media Library search/sort/bulk actions UI (spec 14.38-14.40) — folders (`media_folders`, added after owner feedback) give basic organization, but `/media` is still one flat grid per folder with no search or bulk operations | Out of scope for validating the Pricing Validator itself | Add once an agency actually has enough media that scrolling a folder is a real problem |
